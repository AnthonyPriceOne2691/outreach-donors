# Plan: срез 1.1b `sales-stage`, часть «а» — значение этапа и отказ продажам в письмах

Перенос на main `05d75d9` (06.10): код части — с ветки `sales/1.1b-stage` (проверена на `7085826`),
переложен на механику #175 — учётка платформы по направлению. Перенос 07.10 на main `f9819da` (#196, #194,
#180 с перечнем консоли продаж, #198, #197): консоль — перечнем `cli/sales_commands.py`, отбор пробного
рекламодателя (#192) — по новому имени, отправка очереди пачкой (#191) — отказ продажам словами; `check_ready`
#197 — как в main.

## Approach

- **Значение** — `Stage.SALES` в `backend/features/core/domain.py`; миграция `39e342cb2b21`
  (`ADD VALUE IF NOT EXISTS`, после `fc721be3d031`), откат значение не снимает (обоснование —
  в докстроке `downgrade`).
- **Отказ — один класс и один текст** — `backend/features/core/stages.py`: `SALES_NOT_CONNECTED`,
  `SalesNotConnectedError(what)` с `permanent = True`, шлюз `mail_stage(stage, what) -> MailStage`
  там, где этапу нужен только допуск, и `donor_path` — пометка ветки по `MailStage`, после которой
  остаётся путь доноров. API — 409 строкой в `STATUSES`, консоль — перечнем `FAILURES` в
  `backend/cli/sales_commands.py` (код 9), который `cli/main.py` вливает в `_FAILURES` целиком.
- **Разбор этапа целиком** — `match` с `assert_never` в каждой точке, где этап решает путь:
  `LetterRepository.candidates`/`funnel` (единственный вход отбора), `template.first_letter`,
  `template._followup_prefix` → `CHAINED`. Шлюзы — `building.run_scope`, `Sending._target`,
  `answers._context`.
- **Отправка и учётка этапа (#175)** — `Sending.send` выбирает транспорт этапа письма
  (`of_stage(self._transports, target.stage.value)`) сразу после `_target`. Шлюз продажам стоит в
  `_target`, то есть до выбора транспорта: учётка продаж (`mail_account("sales")`) для письма,
  которое почта не ведёт, не собирается, и отказ — словами среза, а не «Почта этапа не собрана».
  В `_check_review` разбор `MailStage` — `if` рекламодателей и `stages.donor_path(target.stage)`:
  этап, добавленный в `MailStage` без своей ветки, — ошибка mypy в этой строке.
- **Учётка направления** — своей не заводим: ключ, ключ событий и список разрешённых этапа берёт
  `config.outreach.mail_account(stage)`, ключи событий вебхук собирает по всем значениям `Stage` —
  со значением `sales` учётка продаж подхватывается сама (тест на событие, подписанное её ключом).
- **Добивки** — захват берёт только письма рассылок этапов из `template.CHAINED` (подзапрос
  `_chained`); `Chain.unchained` считает подошедшие добивки этапов без цепочки, проход пишет число в
  отчёт (`PassReport.waiting`, рядом с «исход неизвестен» #175) и предупреждение в журнал;
  `SalesNotConnectedError` при отправке добивки возвращает срок (`_deliver`, после ветки
  `MaybeSentError`), как вставший ящик.

- **Отправка очереди пачкой (#191)** — мост подключения этапа `stages.check_connected(session, stage,
  what)`: доноры и рекламодатели — подключены, продажам — `SalesNotConnectedError`; правило «продажи
  подключены» (своя учётка, отправитель, цепочка) встанет в ветку продаж моста и прочтёт базу — маршрут
  не меняется. Маршрут `POST /api/letters/send-queue` спрашивает мост первым — до счёта очереди и до
  задачи: на пустой очереди продаж ответ — «не подключены», а не «писем нет». Пачка
  (`batch._send_one`) ловит `SalesNotConnectedError` вместе с `NoSenderError` до общего `except
  Exception`: следующее письмо этапа упрётся в то же, пачка встаёт с причиной словами.
- **Пробный рекламодатель (#192)** — `crawl/probe_advertiser._taken_first` зовёт отбор рекламодателей по
  имени без этапа `Recipients.advertiser_candidates(limit=1)` — тот же запрос сборки; его тест подменяет
  то же имя.

## Rejected alternatives

- Своя копия выбора учётки в модуле продаж (свои переменные, свой транспорт) — отклонено: #175 уже
  выбирает учётку по этапу; вторая копия разошлась бы с первой (решение владельца 05.10: механизм
  общий, конфиг направления — их).
- Отказ продажам после `of_stage` (в `_check_review`) — отклонено: транспорт продаж собирался бы для
  письма, которое почта не ведёт, а без своей учётки отказ звучал бы «Почта этапа «sales» не
  собрана», а не причиной.
- `match` с `assert_never` в `_check_review`, как на старом main, — отклонено при переносе: после
  #175 `sending.py` — 498 строк, `match` дал бы 505 при пределе 500; `donor_path` даёт ту же
  проверку mypy одной строкой.
- Отказ продажам одной проверкой на входе API — отклонено, потому что почту зовут ещё консоль,
  задачи очереди и проход добивок.
- Словари по этапу с `.get()` и запасным значением — отклонено: запасное значение и есть «молча донор».
- Разбор этапа внутри `Recipients.candidates` (как было) — отклонено: параметр этапа у пути доноров
  и был дырой.
- Отказ продажам в шаблоне добивки без фильтра в захвате — отклонено: шаблон выбирается уже после
  погашения и фиксации срока.
- Значение в одной ревизии с использованием — отклонено (урок 1.4, `2d9877260a6d`).
- 409 кнопки пачки через шлюз `mail_stage` — отклонено: шлюз отказывает продажам там, где их не будет и
  подключённых, а кнопка пачки продажам понадобится; через выбор учётки этапа — отклонено: «учётка есть»
  не значит «продажи подключены» (отправитель, цепочка), а без учётки отказ звучал бы о транспорте.
- Мост без `session` (функция только этапа) — отклонено: правилу продаж нужна база, и срез отправки
  продаж менял бы подпись моста и вызов в общем маршруте; цена — `# noqa: ARG001` с причиной.
- Отказ продажам в пачке как отказ по одному письму (`refused`, пачка идёт дальше) — отклонено: следующее
  письмо этапа упрётся в то же, и пачка из сотни писем дала бы сотню одинаковых строк отказа.
- Строки консоли продаж в `cli/main.py`, как на старом main, — отклонено: на базе `main.py` — 484 строки
  при пределе 500 и продаж не называет (команды продаж — перечнем `sales_commands.py`); теперь +2 строки.
- Вернуть `Recipients.candidates(stage, …)` ради вызова #192 — отклонено: параметр этапа у пути доноров и
  был дырой «доноры любому этапу».

## Risks

- `letters/sending.py` — 499 строк при пределе 500 (ратчет считает 500): любая строка соседей в
  `sending.py` упрётся в гейт длины. Правки части в `letters/batch.py` и `api/letters/routes.py` (#191) —
  по 3–4 строки.
- `tests/test_probe_donor.py` (#181) и `crawl/probe_advertiser.py` (#192) звали `Recipients.candidates(…)`:
  правки — в части; новые вызовы отбора с этапом у соседей станут ошибкой mypy (имени больше нет).
- Снимок сложности — общий файл всех PR: при каждом переносе — пересборка `scripts/complexity.py --update`.
- Слив части «а» — только после первого письма Этапа 2 (решение владельца 01.10); перед сливом —
  перенос на main после круга соседней сессии (координатор).

## Rollout / migration

Ревизия `39e342cb2b21` только добавляет значение: строки не трогаются, повтор безвреден
(`IF NOT EXISTS`, тест A1 гоняет подъём и откат в процессе). Откат значение не снимает. Ревизия висит на
голове базы `cbc5aadf4fc2` (#180); на голову main после слияния ревизий соседней сессии («цены списком»,
`ad4a79bc6000`) её перецепит координатор.

## Test / eval strategy

`tests/test_sales_stage_mail.py` на настоящей базе дерева: домен письма продаж — заодно принятый
донор с адресом, ящики есть у обоих этапов, — путь доноров дал бы результат, и отказ виден по тому,
чего в базе нет. A2 — с набором транспортов по этапам: о продажах набор не спрошен. Событие учётки
продаж — через API вебхука с ключом из `OUTREACH_SALES_EVENTS_PUBLIC_KEY`. Пачка — `batch.send_queue` с
письмом продаж в очереди; кнопка — `POST /api/letters/send-queue` на пустой очереди и с письмом в ней.
Мутанты — повторно только в местах, переписанных при переносе 07.10 (перечень консоли, вызов #192,
ревизия, мост, пачка, кнопка); места переноса 06.10 и остальные — прежние таблицы.
