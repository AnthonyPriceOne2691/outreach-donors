# Plan: срез 1.4, часть 1.4b+c — очистка базы лидов

## Approach

- **Ступени — от бесплатных к платной.** Правила без сети, одним чтением базы на партию:
  дубль → стоп-лист продаж → общие отписки → чужой диалог → годность; лид под двумя
  правилами назван первым. Затем DNS по домену самого адреса (`mail_route`, параллельно по
  уникальным доменам партии). Платный проверяльщик — только для тех, кто дошёл.
- **Партия — 200 лидов, одна транзакция и одна строка расхода.** Платные вердикты — деньги:
  обрыв прохода не должен терять ни их, ни строку расхода.
- **Провайдер проверки — Hunter Email Verifier** за `Protocol EmailVerifier`, тем же ключом,
  что поиск адресов (`CONTACTS_HUNTER_API_KEY`): сервис один, второй переменной нет. Квота
  общая с другой системой — поэтому квота и закрытая учётка останавливают платную часть
  прохода, а не повторяются; остаток у провайдера не спрашиваем. Разбор отказов и маркеров
  (`restricted_account`, `usage_exceeded`, `too_many_requests`) — общий с поиском адресов
  (`contacts/provider.py`), не копия.
- **По умолчанию `fixture`:** разработка и проверка проводки без денег; источник вердикта
  хранится в `verification_status` (`fixture:*`), отправка (Ф4) обязана его видеть и не слать.
- **Стоп-лист продаж — своя таблица** до появления `Stage.SALES` (1.1b): при его появлении
  переезжает в общие `suppressions` с причиной `manual`.
- **Причины отказа — перечисление в коде** (`RejectionReason`, `String(32)` в базе) и слова
  в `cleaning_note`: новая причина — строка кода, а не миграция; экран 1.5 фильтрует по коду.

## Rejected alternatives

- Отдельный сервис проверки адресов — отклонено: второй ключ, второй договор, второй разбор
  отказов; выигрыш в точности не доказан, а Hunter уже в коде с боевыми уроками.
- SMTP-разговор со своего IP — отклонено: бьёт по репутации и запрещён многими серверами.
- Одна транзакция на весь проход — отклонено: обрыв терял бы оплаченные вердикты и строку
  расхода.
- Своя проверка MX — отклонено: один `mail_route` у всех направлений (правило «один раз»);
  нулевой MX и запасные резолверы — там.
- Буквальное чтение отписок «только `stage NULL`» — отклонено: приём ответов писал отписку
  с этапом, отписавшиеся через ответ прошли бы в рассылку.
- Строки `suppressions` со `stage=sales` для стоп-листа продаж — отклонено: значения `sales`
  в `Stage` нет до 1.1b.
- Тип Postgres для причин отказа — отклонено: каждая новая причина стала бы миграцией.

## Risks

- `fixture` по умолчанию: без переключателя в `live` база очистится выдуманными вердиктами —
  поэтому источник вердикта в статусе и предупреждение в консоли.
- Доля `unknown`/`accept_all` у живого провайдера неизвестна до замера; порог — Ф4.
- Квота общая с соседним модулем: остановка платной части — штатный исход, код выхода 7
  для расписания.
- Живой DNS и живой Hunter на настоящей базе не замерены — «заложено»; DNS на заглушке
  с задержками и молчащими доменами — в verify-report.
- `.test`-зона в тестах не сводится к корню (нет в списке суффиксов): правило корня
  проверено подменой `host_key`, само сведение — тестами `donors/host`.

## Rollout / migration

Одним PR под вейвер владельца (решение 04.10: 1.4b без 1.4c роняет живой проверяльщик после
оплаченной проверки — `UnknownOperationError`, а 1.4b сам больше 800 строк). Две миграции:
`95ee6522e0de` (колонки `sales_leads`, индекс, таблица `sales_stoplist`) после `1f7b0ee634c2`
и `2d9877260a6d` (`ALTER TYPE usageprovider ADD VALUE IF NOT EXISTS 'hunter'`) после неё —
`ADD VALUE` отдельной ревизией, значение в той же транзакции не используется; голова одна.
Слияние в main прод не трогает; выкатка — по отдельному «да» владельца, соседней сессией,
закреплённо по хэшу. `SALES_VERIFIER_PROVIDER` по умолчанию `fixture`: денег после выкатки
не тратится, пока человек не включит `live`.

## Test / eval strategy

Все тесты — на настоящей базе дерева: `tests/test_sales_cleaning.py` (правила A1–A3, A8, A9,
порядок, партии, A4 по заглушке DNS, A5–A6 на уровне прохода, Hunter за `MockTransport`),
`tests/test_sales_stoplist.py` (файл, запись, журнал, CHECK, консоль, цикл миграции),
`tests/test_sales_verifier.py` (вердикты, 15 отказов с классом и словами, `fixture`, фабрика,
A7, расход, миграция `usageprovider` в процессе), `tests/test_sales_clean_cli.py` (сводка,
коды 0/5/7, A7 без касания лидов, подсказка второго Ctrl-C). Новые тесты на старом коде —
красные; обратные прогоны — 24 мутанта по одному на правило (verify-report).
