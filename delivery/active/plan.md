# Plan: контур модуля «Продажи», волна В0

## Approach

**Чистое ядро плюс тонкий вход.** Ядро `scripts/contour_waves.py` — функции без
ввода-вывода: разбор реестра, детекторы, судья, печать. Файлы читает и git
спрашивает одна функция `collect`. Вход — CLI:
- `--base <ref>` — CI передаёт ветку назначения PR или `before` push, pre-push — `origin/main`;
- `--warn` — режим pre-push: нарушение печатается предупреждением, выход 0;
- `--root` — корень дерева (тесты), `--canon` — где лежит канон (только `--warn`).

**Детекторы — данными, а не ветками судьи** (таблица `DETECTORS`):
- `sales-code` — файлы под `backend/features/sales/` в дереве PR;
- `sales-in-base` — они же в базе PR: так читается предел «мерж второго PR продаж»;
- `sales-prompt` — `backend/features/sales/**/prompts/*.md`;
- `sales-llm` — импорт `backend.shared.llm` в `.py` продаж;
- `sales-agent-prompt`, `sales-segment-prompt`, `sales-autosend`,
  `sales-thresholds` — `later`: имя или маркер назовёт срез, который их
  приносит. До тех пор проверка печатает, что волну судит человек;
- `manual` — решает человек; `canon-ahead` — канон рядом ушёл вперёд (только
  pre-push); `this-pr` — предел «мерж этого PR».

Новый детектор — строка в таблице. Неизвестный id в реестре — ошибка разбора.

**Судья.** Волна `pending` нарушена, когда её предел наступил: `this-pr` —
триггер сработал в дереве PR, иначе — сработал детектор предела. Триггер есть,
предел впереди — сведение «триггер сработал, предел — …» (A4). Волна
`deployed` предъявляет улику: пути из колонки «Доказательство» существуют,
у В1 в `.importlinter` есть контракт с `backend.features.sales`, у В2 есть
понятие OKF с `implementation:` в продажах, а у волны с триггером
`sales-prompt` каждый промпт назван в `model_surface` (A6).

**Объявления, независимые от реестра:** `stack-selftest:` в STACK-ACCEPTANCE или
STATUS (A9); у среза `sales-*` — раздел «Уроки» с пунктами (A10) и
`shared_changes:` на каждый тронутый файл вне путей продаж (A13).

**Краснеет только PR, несущий работу продаж.** STATUS один на репозиторий, и
PR доноров идут при активном срезе продаж, не трогая его (#122, #125, #127 —
ни один не правил `delivery/active/STATUS.md`). Если судить по одному slug,
после мержа В0 каждый их PR с правкой общего кода покраснел бы на A13, а после
первого PR продаж — на пределе В1. Протокол сети проектов это запрещает:
соседу нельзя ронять чужой коммит. Поэтому PR несёт работу продаж, если его
дифф трогает пути продаж, реестр или проверку волн, а при срезе `sales-*` —
ещё и `delivery/active/`. Остальные PR печатают те же находки предупреждением
и строкой «PR не несёт работы продаж»; A10 и A13 к ним не применяются. Нет
базы — чей PR, не узнать, и судим строго.

**Где живёт проверка — отдельный `scripts/contour_waves.py`, а не правило
в `scripts/gates.py`.** Решение по устройству `gates.py`: один код выхода на все
правила и ни одного режима — нет ни `--warn`, ни `--base`, а проверке волн нужны
оба. Плюс объём: `gates.py` — 368 строк, проверка волн — 460, вместе
файл перешёл бы предел в 500 строк.

**Срез В0 сам трогает общий код** (CI, хук, новый скрипт) — и объявляет это
в своём STATUS строкой `shared_changes:`, а не получает исключение по имени.
Правило одно для всех срезов `sales-*`; исключение по slug было бы скрытым
обходом той же проверки. Заодно это первый прогон A13 на настоящем дереве.

**Подключение.**
- CI: шаг «Волны контура модуля «Продажи»» в джобе `check` файла
  `.github/workflows/ci.yml`, после «Подпись необратимого». Мерж держит только
  обязательная проверка, а обязательны `check`, `web` и `docker`: `quality`
  не обязательна, и `merge_guard.sh`, который требует её зелёной, обходится
  через `gh pr merge`. Базу шаг определяет сам, лестницей шага «Diff base»
  из `quality.yml` без тихой ступени: PR — `git fetch` ветки назначения и база
  `origin/$GITHUB_BASE_REF`; push в main — `before`; нулевой или недостижимый `before` —
  `::error::`, а не суд над пустым диффом (урок `cqg@2.34`). Checkout в
  `check` — с полной историей: на глубине 1 общего предка с базой нет.
  Джоба `check` идёт до первого красного шага, как и прежде: красная проверка
  волн, как и красная подпись, оставляет ратчет и тесты непрогнанными.
- pre-push: `scripts/hooks/pre-push` с `--warn --base origin/main`, до проверки
  `.venv` — проверке хватает `python3`. Упавшая проверка печатает причину
  и пуш не держит.

## Stack / boundaries

Только стандартная библиотека Python. Читает `delivery/` и `okf/`, пути под
`backend/features/sales/`, `.importlinter`; git — `ls-tree` базы и
`diff base...HEAD`. Ничего не пишет.

## Rejected alternatives

- Чеклист в плане фаз без механизма — отклонён, потому что правило, которое
  надо помнить, не исполняется.
- Расширить канонный `delivery_check.py` — отклонено, потому что канон
  не правится из проекта; если класс общий, его путь — `upstream-candidate`.
- Краснеть на pre-push — отклонено, потому что по протоколу сети проектов
  механизм, мешающий работать, снимают первым: рабочий пуш агента проходит.
- Даты как пределы — отклонены, потому что репозиторий публичный, а дату
  машина не проверит.
- Правило в `scripts/gates.py` — отклонено, потому что у него один код выхода
  без режимов, а вместе файл перешёл бы 500 строк.
- Исключить срез В0 из A13 по имени — отклонено, потому что исключение по slug
  — скрытый обход; честнее объявить свой дифф общего кода.
- Судить A13 и пределы волн по одному slug активного среза — отклонено,
  потому что PR доноров идут при активном срезе продаж и покраснели бы на
  своём же общем коде: ложный красный на PR доноров — первый риск спеки.
- Шаг CI в джобе `gates` — отклонён, потому что её шаги до pre-commit идут без
  `if: always()`, и красный шаг унёс бы установку и все гейты.
- Шаг CI в джобе `delivery` файла `quality.yml` (так было в T5) — отклонён на
  ревью, потому что `quality` не обязательная проверка: красный шаг там мерж
  не держит, а `merge_guard.sh` обходится через `gh pr merge`.

## Risks

- Ложный красный на PR доноров. Защита: без `sales/` и не у среза `sales-*`
  проверка зелёная (A1), база ей не нужна.
- Тихий зелёный самой проверки. Защита: обратные прогоны тестом и правило
  «гейт обязан отклонять шаблон»: шаблонная строка реестра, пустой раздел
  «Уроки» и `shared_changes` без согласования — красные.
- Хрупкий разбор таблицы. Защита: A12 — ошибка с номером строки.
- Детекторы `later` не судят ничего, пока их не назовут. Защита: строка
  «пока волну судит человек» при каждом прогоне с кодом продаж.

## Rollout / migration

Одним PR. Без файлов `sales/` проверка ничего не меняет срезам доноров.
Откат — убрать шаг из `ci.yml` и строку из хука.

## Test / eval strategy

- `tests/test_contour_waves.py`: по тесту на каждый пример A1–A13; A2–A5 и A13 —
  во временном git-репозитории с двумя коммитами (база и голова).
- Обратный прогон файлом: маска кода продаж не совпадает ни с чем — сценарии
  A2 и A5 зеленеют, то есть их тесты упали бы.
- Новые тесты сначала прогнаны на заглушке проверки — обязаны упасть.
- Прогон на дереве ветки: без `sales/` — зелёный; с подложенным
  `backend/features/sales/__init__.py` — по примерам A2, A4 и A5.
- Ссылка на продуктовые оракулы — `eval-smoke.md`.

Уроки архива (`delivery/archive/INDEX.md`, L1 и L2) не применимы: их пути —
`robots/` и `billing/`, дифф среза их не трогает. Прочитанные уроки — в `tasks.md`.
