# Plan: срез 3.1 `sales-kb` — база знаний агента и настройки отправителя

## Approach

- **Данные** — `backend/features/sales/models.py`: `SalesKbEntryModel` (`sales_kb_entries`, тип
  `sales_kb_kind`, ключ `uq_sales_kb_entries_key` «вид, язык, заголовок», теги `ARRAY`) и
  `SalesSettingsModel` (`sales_settings`, одна строка — `ck_sales_settings_one_row`). Миграция
  `c6efe4e5de7e` создаёт обе таблицы и тип; значение журнала — отдельной ревизией `a51e5688f79e`
  (`ADD VALUE`, как `2d9877260a6d` у 1.4).
- **Правила** — `backend/features/sales/kb.py`: приведение полей (`entry`), ключ (`_key_free`),
  выборка агента (`facts`), версия (`version_of`/`version`), группы (`grouped`), заведение и правка
  с журналом (`add`, `change`). `backend/features/sales/sender.py`: поля и формы ссылок
  (`cleaned`), запись целиком с журналом (`save`), перечень недостающего (`Sender.missing`) и
  проверка готовности для Ф4 (`check_ready`, правило `REQUIRED`: адрес, подпись, имя).
- **API** — `backend/api/sales/kb.py` + `kb_schemas.py`, роутер входит в роутер раздела
  (`routes.py`); отказы — через `backend/api/errors.py`.
- **Консоль** — `backend/features/sales/kb_load.py` (чтение, план, запись) и
  `outreach sales-kb-load` в `backend/cli/sales.py` / `main.py`.
- **Экран** — `frontend/src/sales/`: `KbPane.tsx`, `KbEntryModal.tsx`, `AgentPreview.tsx`,
  `SenderPane.tsx`, `kbData.ts` (запросы), `kbDraft.ts` (черновик и отказы до нажатия); клиент,
  типы и подписи — `api/sales.ts`, `api/salesTypes.ts`, `api/salesLabels.ts`; вкладки — в
  `SalesPage.tsx`. Границы полей — из ответа сервера (`limits`).
- **Замеры** — каталог `scripts/ui_screens_sales.py` (шесть экранов), `ui_contrast.py`,
  `ui_hover.py --path`.

## Rejected alternatives

- Версия базы счётчиком правок или временем последней правки — отклонено, потому что откат
  правки должен возвращать прежнюю версию, а черновик (Ф3.2) — узнавать базу по строке версии;
  отпечаток содержимого это даёт, счётчик — нет.
- Отдельный запрос для предпросмотра «что увидит агент» — отклонено, потому что предпросмотр
  со своим фильтром показал бы не то, что получит агент, когда правила выборки разойдутся; экран
  и версия зовут `kb.facts`.
- Удаление записей — отклонено, потому что выключенная запись сохраняет текст и след в журнале,
  а удалённая пропадает вместе с ответом на вопрос «из чего агент писал вчера».
- Настройки отправителя ключ-значением или в окружении — отклонено, потому что набор полей
  задан спекой и экраном, правка окружения требует выкатки и не видна в журнале; одна строка с
  типизированными колонками и `CHECK id = 1`.
- Адрес доноров (`OUTREACH_POSTAL_ADDRESS`) запасным адресом продаж — отклонено, потому что у
  продаж свой отправитель, и подставленный чужой адрес выглядел бы заданным (A3).
- Проверка готовности «только адрес и подпись» — отклонено владельцем 05.10, потому что в From
  должно стоять настоящее имя (конституция); имя — третье правило `REQUIRED`.
- `PUT` для отправителя — отклонено, потому что клиент экрана умеет GET/POST/PATCH (как у
  порогов), а правка общего `client.ts` — вне точек среза; запись целиком — `POST`.
- CSV для загрузки базы — отклонено, потому что текст записи — абзацы, а в CSV их держали бы в
  кавычках со сдвоенными кавычками; JSON собирают программой или в редакторе.
- Загрузка частями (что прочиталось — то легло) — отклонено, потому что база по половине фактов
  — это агент, который пишет по половине фактов; всё или ничего с номерами записей.
- Перезапись отличающихся записей при повторной загрузке по умолчанию — отклонено, потому что
  запись могли поправить на экране после первой загрузки, и старый файл молча откатил бы правку;
  только с `--update`.
- Чтение файла из копии репозитория — отклонено, потому что факты компании — коммерческий текст,
  а `git add .` унёс бы его в публичную историю; отказ до чтения.
- Значение журнала в миграции таблиц — отклонено, потому что `ADD VALUE` нельзя использовать в
  той же транзакции (урок 1.4); отдельная ревизия.
- Мерить значения однострочных полей окна записи — отклонено, потому что вырезка берёт кромку
  поля из чернил и даёт 2,74 при 5,0–6,4 по строке букв (слепое пятно, как в `ui_screens.py`);
  меряется текст записи длинным текстом.
- Правка общего `glass.css` под замер окна — отклонено, потому что провала нет (14,5 : 1 по
  цветам), а кромка из чернил — общее решение плотного стекла светлой темы.

## Risks

- Версию пишет Ф3.2 — формат `kb-` + 12 знаков зафиксирован тестом; смена канона отпечатка
  (поля, сведение пробелов) меняет версии всех черновиков — только с миграцией смысла.
- Ключ записи сводит пробелы в заголовке, но не регистр: «Цена» и «цена» — две записи.
- Загрузка держит всю базу в одной транзакции — для десятков записей это миллисекунды; файл
  больше 2 МБ отказывается словами.
- Миграции соседней сессии (агент переписки) могут войти в main раньше: тогда
  `c6efe4e5de7e.down_revision` перецепить на их голову и прогнать цикл миграций.
- Живой прогон — на своей базе и выдуманных записях; на настоящих текстах — заложено.

## Rollout / migration

Две миграции (`c6efe4e5de7e` → `a51e5688f79e`), только создают: на живой базе данные не
трогаются. Откат снимает таблицы и тип `sales_kb_kind` (цикл под тестом). Значение журнала
`sales_kb_changed` откатом не снимается — `ADD VALUE` необратим в PostgreSQL, повтор не ломается
(`IF NOT EXISTS`, тест повтора).

## Test / eval strategy

Тесты на настоящей базе дерева (A1–A3, ключ, журнал, цикл миграции), API через `httpx` (403 на
каждом маршруте), консоль через `build_parser` и `main`; vitest через `serve()` (незаписанный
запрос роняет тест); сверка кодов сервера с экраном (`tests/test_sales_kb_screen.py`). Красный
прогон на main без кода среза; мутанты версии, выборки, готовности. Замеры A4 — живьём
(verify-report).
