# Spec: модуль «Продажи», срез 1.4 — часть 2 из 2 (1.4b+c): очистка базы лидов

**Problem.** До первого письма лид продаж проходит отсев: дубли, стоп-лист владельца базы,
отписавшиеся где угодно, адреса чужих отделов и заглушки, домены без почты, мёртвые ящики.
Каждый отказ доставки бьёт по репутации почтового домена — ресурсу, который не
восстанавливается. Проверки адреса в сервисе не было: только MX домена и поиск адресов.
Часть 1 (страна кодом и часовой пояс) слита отдельным PR.

## In scope

- **Дубли (A1).** Внутри файла и против всех лидов продаж по адресу: оригинал — наименьший
  `id` с этим адресом в любой гипотезе и с любой судьбой; повтор — `rejected: duplicate`,
  словами «дубль: адрес уже у лида №N». Дубль через границу партий виден по базе.
- **Домен в работе у другого направления (A2).** Домен компании лида в диалоге доноров или
  рекламодателей со статусом `open` или `replied` → `rejected: other_direction`. `closed`
  и `unsubscribed` диалог не держат — отписку держит общий стоп-лист.
- **Стоп-лист продаж.** Без `Stage.SALES` (срез 1.1b отложен) — своя таблица `sales_stoplist`:
  домен или адрес (CHECK «ровно одно»), кто и когда внёс, заметка-источник. Загрузка файлом
  (`outreach sales-stoplist-add`): первая ячейка строки — домен или адрес, первая нечитаемая
  строка файла — заголовок, остальные нечитаемые названы с номером строки, повтор считается
  отдельно от «добавлено», одна запись журнала на загрузку. Лида закрывает адрес, домен
  компании, домен самого адреса и его корень (`host_key`) → `rejected: stoplist`.
- **Отписки (A3).** Общие `suppressions` через `in_force`: строки без этапа любой причины плюс
  `unsubscribed`/`complained` любого этапа — приём ответов писал отписку с этапом кампании,
  и буквальный «только `stage NULL`» пропустил бы отписавшихся через ответ (соседний #154
  переводит такие записи на «без этапа»; чтение остаётся верным для старых и новых строк).
  `manual`/`supplier` с этапом — правила чужих направлений, продажи их не держат. Срок
  записи уважается. По адресу и по домену компании → `rejected: unsubscribed`.
- **Годность адреса.** Общий `contacts/quality.rejection_reason` целиком (отделы `legal`,
  `privacy`, `hr`, `datenschutz`…, заглушки) плюс своё правило «ролевой ящик на бесплатной
  почте — чужой личный, а не роль компании» (`info@gmail.com`) → `rejected: unusable`,
  причина — словами правила.
- **Почта домена самого адреса (A4).** `contacts/mx.mail_route` по домену адреса лида, не
  компании; один запрос DNS на уникальный домен партии, параллельно (`Semaphore 8`), повтор
  на таймауте внутри `mail_route`. `NONE` и `NULL_MX` → `rejected: no_mail` без платной
  проверки; `MX`, `IMPLICIT`, `UNKNOWN` — дальше; доля `UNKNOWN` — отдельное число сводки.
- **Платный проверяльщик (A5–A7).** `Protocol EmailVerifier`, реализации `fixture` (вердикт по
  началу локальной части, без сети и денег, уверенность некруглая) и `live` — Hunter Email
  Verifier тем же `CONTACTS_HUNTER_API_KEY`. Выбор — `SALES_VERIFIER_PROVIDER`, по умолчанию
  `fixture`; `live` без ключа — `ConfigError` до первого лида (A7). Вердикт
  `invalid`/`disposable` → `rejected: undeliverable` («адрес не существует» / «одноразовый
  ящик»); `valid`/`webmail`/`accept_all`/`unknown` → `ready` — «провайдер не знает» тоже
  вердикт (решение владельца 04.10, порог — в Ф4). Отказ сервиса — сеть, 429, 5xx, 202,
  не JSON, незнакомый статус — лид остаётся `new` с «проверка не выполнена: …» и повторяется
  (A6); квота и закрытая учётка останавливают платную часть прохода — остальные лиды всех
  партий остаются `new` с той же причиной, бесплатные правила им применены.
- **Запись.** `sales_leads`: `status`, `rejection_reason` (код `RejectionReason`, String(32)),
  `cleaning_note` (слова), `verification_status` вида `hunter:valid` / `fixture:unknown`
  (источник виден — выдуманный вердикт не спутать с живым), `verification_score`, `verified_at`.
- **Расход.** Операция `sales_verify` → `UsageProvider.HUNTER` (новое значение, миграция
  `2d9877260a6d`): одна строка на партию, единица — проверка; `fixture` строк не пишет.
- **Проход.** `outreach sales-clean [--hypothesis]`: лиды `new` всех или одной гипотезы, партии
  по 200 с коммитом каждой, сводка словами, код выхода 7 при остановке платной части
  (решение владельца 04.10). Лид `ready` второй раз не проверяется. Второй Ctrl-C говорит,
  что записанные партии остались в базе; у `sales-import` — что загрузка одной транзакцией.

## Out of scope

Экран лидов (1.5); `Stage.SALES` и переезд стоп-листа в `suppressions` (1.1b); порог по
`unknown`/`accept_all` при отправке (Ф4); живой замер DNS и Hunter на настоящей базе
(«заложено»: сценарии и числа на заглушке — в verify-report); XLSX.

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| A1 | адрес уже у лида продаж (в файле или в базе, любая гипотеза) | `rejected: duplicate`, «дубль: адрес уже у лида №N» |
| A2 | домен компании в `open`/`replied` диалоге доноров или рекламодателей | `rejected: other_direction`; `closed`/`unsubscribed` диалог не держит |
| A3 | отписка без этапа; отписка или жалоба с этапом; домен компании в общем стоп-листе | `rejected: unsubscribed`; срок записи уважается |
| A4 | домен самого адреса `NONE` или `NULL_MX` | `rejected: no_mail`, проверяльщик не вызван; `UNKNOWN` идёт дальше и считается в сводке; один запрос DNS на домен |
| A5 | проверяльщик: `invalid` / `disposable` | `rejected: undeliverable`, `verification_status` = `hunter:invalid`; `fixture` — без строки расхода |
| A6 | 429, 5xx, 202, не JSON, незнакомый статус | лид `new`, «проверка не выполнена: …», повтор следующим проходом; квота или закрытая учётка — остановка платной части, остальные `new`, код выхода 7 |
| A7 | `SALES_VERIFIER_PROVIDER=live` без ключа | `ConfigError` на старте, ни один лид не тронут |
| A8 | адрес, домен компании, домен адреса или его корень в `sales_stoplist`; файл стоп-листа с заголовком, мусором и повтором | `rejected: stoplist`; добавлено / повтор / нечитаемые строки с номерами, одна запись журнала |
| A9 | `privacy@`, `noreply@`, заглушка, `info@gmail.com` | `rejected: unusable` словами правила |
