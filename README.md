# Outreach Donors

Поиск сайтов-доноров по выдаче Google, проверка их метриками Ahrefs и сбор
цен размещения по email.

Прогон: список ключевых слов и страна → выдача → отсев по порогам (регион, DR,
трафик) → база доноров → запрос цены письмом → разбор ответа в поля «цена белая,
цена серая, способы оплаты».

Правила домена, которые нельзя нарушать молча, — в [okf/](okf/index.md):
экономика запросов, пороги отбора, правило региона, сроки годности.
Процесс и неотменяемые решения — в [delivery/](delivery/CONSTITUTION.md).

## Стек

Python 3.12+, FastAPI, PostgreSQL 16, Redis, SQLAlchemy 2 + Alembic.

## Запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
cp .env.example .env            # заполнить ключи
docker compose -f docker-compose.dev.yml up -d
.venv/bin/alembic upgrade head
```

Порты на хосте нестандартные — 5442 и 6389. Рядом живёт соседняя система,
она занимает 5432 и 6379.

## Сервер

```bash
.venv/bin/uvicorn backend.api.main:app --reload --port 8100
```

Схема API и песочница — `http://127.0.0.1:8100/api/docs`. Без
`ACCESS_JWT_SECRET` сервер не стартует: пустой секрет означал бы вход
без проверки подписи, и узнать об этом лучше при развёртывании, чем
от сотрудника, который не может войти.

За обратным прокси запускать с `--proxy-headers`, а прокси обязан
передавать настоящий адрес клиента: иначе счётчик попыток входа видит
адрес прокси и считает весь интернет одним посетителем.

## Весь стек в докере

```bash
cp .env.example .env            # заполнить POSTGRES_PASSWORD и ACCESS_JWT_SECRET
docker compose up -d --build    # фронт, сервер, воркер, очередь, база
docker compose exec api outreach user-add --email ivan@site.com --role admin
```

Интерфейс — `http://localhost:8090` (порт меняется `WEB_PORT`). Наружу
смотрит только nginx: он отдаёт собранный фронт и проксирует `/api` на
сервер. База и очередь опубликованы не наружу, а в сеть докера —
к ним ходят контейнеры.

Что где:

| Контейнер | Что делает |
|---|---|
| `web` | nginx: собранный фронт и прокси на `/api` |
| `api` | сервер FastAPI, проверка живости ходит в базу |
| `worker` | очередь прогонов (rq), слушает `runs` |
| `reaper` | разбор мёртвых прогонов: продолжает осиротевших, закрывает безнадёжных |
| `followups` | добивки: второе и третье письмо цепочки уходят по сроку |
| `postgres`, `redis` | база и очередь, тома переживают пересоздание |
| `migrate` | одноразовый: `alembic upgrade head` до старта остальных |

Песочница выдачи включена по умолчанию (`SERP_SANDBOX=true`): живой ключ
тратит деньги, и переключение в бой — решение человека, а не следствие
того, что сервис уехал на сервер. Песочница вместе с живым ключом Ahrefs
запрещена отдельно — домены там выдуманные, а метрики по ним платные.

Разработка без контейнеров прежняя: `docker-compose.dev.yml` поднимает
только базу и очередь на 5442 и 6389, а сервер, фронт и воркер очереди
запускаются руками.

## Воркер очереди

```bash
.venv/bin/python -m backend.workers.main        # слушает очередь `runs`
```

Без воркера сборка писем, разбор ответа и прогон, поставленные из
интерфейса, просто копятся: сервер отвечает «поставлено», экран
показывает успех, и на этом всё кончается — навсегда и без единой
записи о том, что задачу никто не взял. В докере воркер поднимается
сам, в разработке — нет, и это ровно то отличие, при котором
неработающий сервис выглядит работающим.

Рядом с воркером живёт разбор мёртвых прогонов — он продолжает те,
чью задачу убил умерший воркер, и закрывает те, которые продолжать уже
нечем:

```bash
.venv/bin/python -m backend.workers.reaper       # проход раз в минуту
```

Без него прогон, у которого умер воркер, остаётся «идёт» навсегда:
экран показывает работу, которой нет. Продолжение не покупает выдачу
второй раз — она лежит в строке прогона с первой попытки.

Третий фоновый процесс — добивки. Второе и третье письмо цепочки уходят
по сроку, заданному при создании рассылки:

```bash
.venv/bin/python -m backend.workers.followups   # проход раз в минуту
```

Без него цепочка кончается на первом письме и молчит: срок в базе стоит,
а забрать его некому.

**На macOS воркеру нужна переменная `OBJC_DISABLE_INITIALIZE_FORK_SAFETY`:**

```bash
OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES .venv/bin/python -m backend.workers.main
```

rq выполняет задачу в дочернем процессе через `fork`, а библиотеки macOS
после инициализации своего рантайма это запрещают и валят процесс. Падает
любая задача, ещё до первой строки нашего кода, и выглядит это как дефект
задачи: «Work-horse terminated unexpectedly; waitpid returned 6 (signal 6)».
На Linux — то есть в докере и на сервере — такого нет.

## Фронт

```bash
cd frontend && npm ci
npm run dev            # http://localhost:5173, запросы на /api идут в прокси
```

Прокси ведёт на `http://127.0.0.1:8100`; другой адрес — `VITE_PROXY_TARGET`.
Сборка `npm run build`, проверки — `npm run lint`, `npm run typecheck`,
`npm test`. Тесты интерфейса не ходят в сеть и не поднимают базу: они
проверяют, что показано и что отправлено, против записанных ответов.

**Вид** — жидкое стекло: полупрозрачные панели, размывающие полотно,
две темы и переключатель в подвале меню. Рецепт и причины каждого числа —
в `frontend/src/styles/glass.css`. Контраст текста поверх стекла меряется
не на глаз: `python scripts/ui_contrast.py <почта> <пароль>` поднимает
браузер, снимает экран и считает отношение по пикселям.

## Домены рассылки и боевая отправка

Ящики заводятся из консоли, а не из интерфейса: строка отправителя
имеет смысл только вместе с настроенным DNS, и кнопка в вебе позволила
бы завести ящик раньше, чем он способен подписывать письма.

```bash
.venv/bin/outreach sender-add --email outreach@mail-a.example   # домен берётся из адреса
.venv/bin/outreach senders                                      # что заведено и на каком разгоне
```

Разгон считается от даты заведения ступенями `OUTREACH_WARMUP_CAPS`
(по умолчанию 5 → 10 → 15 → 20 писем в день), а не хранится числом:
пропущенный день иначе означал бы ящик, застрявший на пятом письме.

**Боевой транспорт включается одной настройкой** и только после того,
как у доменов настроены SPF, DKIM и DMARC, а у платформы — Domain
Authentication:

```bash
OUTREACH_TRANSPORT=sendgrid
OUTREACH_SENDGRID_API_KEY=…
OUTREACH_ALLOWED_RECIPIENTS=anna@наш-домен.example   # предохранитель первых дней
```

Пока список разрешённых получателей не пуст, письма уходят только
на свои адреса — так проверяются формат письма, заголовки цепочки
и кнопка отписки. Пустой список означает боевую рассылку, и каждое
письмо говорит об этом строкой в логе: тихо перейти из проверки
в рассылку нельзя.

## Страница отписки

Адрес отписки в письме ведёт на сам сервер: `/api/unsubscribe/<метка>`.
Страница отдаётся готовой разметкой, без фронта и без скриптов — ссылка
из письма обязана открыться у кого угодно и через год, а одностраничное
приложение упало бы вместе со своей сборкой.

```bash
OUTREACH_UNSUBSCRIBE_URL=https://наш-адрес/api/unsubscribe
OUTREACH_INBOUND_SECRET=$(openssl rand -hex 32)   # им подписана метка
```

Без секрета ссылка не собирается, и отправка откажет: адрес страницы
без метки не отписывает никого, а письмо с ним выглядит законным.

Переход по ссылке ничего не меняет — он показывает вопрос; пишет
нажатие кнопки. Тем же `POST` приходит отписка в один клик из интерфейса
почты (RFC 8058). Отписка закрывает донора целиком, снимает его письма
с очереди и гасит сроки добивок; почему так — `okf/unsubscribe.md`.

## Экраны оператора

Три места, где раньше требовался инженер с консолью:

- **Контакты** — карточка на экране доноров: сколько ждёт адреса,
  кнопка «Найти контакты» (задача очереди) и отчёт прошлого прохода
  по ступеням лестницы.
- **Формы** — отдельный раздел: доноры, у которых лестница нашла форму
  и не нашла почты. Вписать адрес или закрыть без него; оба исхода —
  в журнал. Остаток месячного потолка показан числом.
- **Выгрузка** — кнопка на экране доноров, CSV по текущему фильтру.
  Точка с запятой и метка порядка байтов ради Excel.

Консольная команда `outreach contacts` осталась и делает ровно то же:
порядок работы живёт в ядре, у кнопки и у команды один путь.

## Команды

```bash
.venv/bin/outreach user-add --email ivan@site.com --role admin   # первая учётка
.venv/bin/outreach user-reset --email ivan@site.com              # новый разовый пароль
.venv/bin/outreach quota                   # остаток юнитов у провайдера, бесплатно
.venv/bin/outreach keywords --preset reviews --country Germany --language German --cap 100 --out ключи.txt
.venv/bin/outreach run --keywords ключи.txt --country us
.venv/bin/outreach contacts --limit 100    # поиск адресов подходящим донорам
.venv/bin/outreach contacts --no-paid      # только бесплатные ступени
.venv/bin/outreach letters-build --campaign «Май» --limit 50   # собрать очередь писем
.venv/bin/outreach letters                 # что стоит в очереди и с каким отличием
.venv/bin/outreach letters-send --id 42    # отправить одно письмо
.venv/bin/outreach demo-seed              # выдуманные домены и переписка — посмотреть экраны
.venv/bin/outreach demo-seed --clear      # убрать выдуманное
```

Ключи берутся двумя способами: своим списком или сборкой по обкатанному
пресету — углы, добор и дедупликация происходят внутри
(`docs/KEYWORD_MODES.md`).

Первая учётка заводится только командой: открытая регистрация «пока база
пуста» — окно, в которое успевает зайти чужой. Дальше админ заводит
остальных сам. Разовый пароль показывается один раз, в базе остаётся хеш.

Поиск контакта идёт ступенями от бесплатных к платной: MX, страницы сайта,
RDAP, платный сервис, форма в ручную очередь. Порядок и его цена описаны
в `okf/contact-ladder.md`; отчёт прогона показывает отдачу каждой ступени.

Письма собираются по шаблону из зон: приветствие, вступление и вопрос
переписывает модель под конкретного донора, а оффер, условия, подпись
и юридический блок она не видит вовсе (`okf/letter-zones.md`). Сборка
ничего не отправляет — отправляет человек, глядя на текст.

Ответы принимаются вебхуком почтовой платформы (`POST /api/inbound/replies`,
секрет заголовком) и разбираются в цены задачей очереди: белая, серая,
способы оплаты, срок размещения. **Спорный разбор уходит человеку,
а не в базу** — приёмка требует не более 5% ошибок, и без этой ветки
порог не держится (`okf/reply-parsing.md`).

**Наружу пока не уходит ничего.** Транспорта нет: двадцати почтовых
доменов не заведено, и `OUTREACH_TRANSPORT=null` отказывается писать
на любой адрес, кроме выдуманного. Отправка отказывает и до тех пор,
пока не заполнены имя отправителя, физический адрес и страница отписки:
без них рассылка нарушает законы почти во всех целевых странах.

## Выкатка и бэкапы

Сервис **ещё не развёрнут ни разу** — решение Anthony 21.09.2026: катим,
когда будут двадцать почтовых доменов и учётка SendGrid. Готово к этому
дню следующее.

**Образы публикуются из CI** при слиянии в `main`:
`ghcr.io/anthonypriceone2691/outreach-donors-backend` и `…-web`, метки —
SHA коммита и `main`. Выкатка становится `docker compose pull`, а не
сборкой на сервере: сборка фронта берёт 2–3 ГБ памяти рядом с работающей
соседней системой.

**Боевые отличия** — в `docker-compose.prod.yml`: лимиты памяти и
процессора у каждого сервиса, потолок журналов, фронт слушает только
петлю. Наружу смотрит обратный прокси хоста, общий с соседом, —
`deploy/proxy/outreach.conf`, два поддомена и один сертификат.

```bash
scripts/backup.sh                                # снять копию
scripts/restore.sh backups/<дата>                # покажет, что сделает
scripts/restore.sh backups/<дата> --yes          # выполнит
```

Бэкапится один том — `pgdata`: очередь пересобирается запуском, и
вчерашняя задача из копии хуже её отсутствия. Что список томов в
компоузе и в скрипте не разошёлся, проверяет
`tests/test_backup_covers_state.py`.

Внешнее хранилище ещё не выбрано, поэтому выгрузка задаётся командой:
`BACKUP_UPLOAD='rclone copy {} storage:outreach/'`. Без неё скрипт
говорит вслух, что копия осталась на том же диске, что и база.

Порядок первой выкатки целиком — [deploy/README.md](deploy/README.md).

## Проверки

Хук перед отправкой прогоняет всё то же, что и CI, — но до пуша, а не после.
Путь к хукам в `.git/config` не переносится клонированием, поэтому включается
одной командой:

```bash
git config core.hooksPath scripts/hooks
```

Аварийный обход — `git push --no-verify`. Дальше него обхода нет.

## Как попадает код

Прямые коммиты в `main` запрещены на стороне GitHub. Порядок такой:

```bash
git switch -c короткое-имя-ветки
git commit && git push -u origin HEAD
gh pr create --fill && gh pr merge --squash --auto
```

`--auto` сольёт ветку сам, когда CI станет зелёным. Если красный — не сольёт
никогда, и это не дисциплина, а механика: кнопка слияния заблокирована,
пока обязательная проверка не прошла.

Правило распространяется на всех, включая владельца репозитория. Ревьюер
не требуется — проверку делает CI, а не человек.


```bash
.venv/bin/ruff check backend/ && .venv/bin/ruff format --check backend/
.venv/bin/mypy backend/
.venv/bin/python scripts/gates.py
.venv/bin/python scripts/complexity.py
.venv/bin/pytest
```

Ратчет сложности держит уже достигнутый уровень: код может становиться
проще, но не сложнее. Жёсткие пороги линтера ловят обвал, ратчет — медленный
рост, при котором каждый отдельный шаг законен. Изменили форму кода —
принять новый уровень командой:

```bash
.venv/bin/python scripts/complexity.py --update
```

## Раскладка

```
frontend/     React 19, Vite, Mantine, TanStack Query — вход и админка
backend/
  api/        веб-слой: маршруты, схемы запросов, зависимости
  config/     настройки по доменам; обращения к окружению только здесь
  features/
    core/     модели и перечисления домена
  shared/     база данных
  migrations/ Alembic
```

FastAPI живёт только в `api/` — это проверяет гейт `layers`. Правил
в веб-слое нет: обработчик передаёт ядру то, что нажал человек, и
показывает то, что ядро решило.

Домен = папка, внутри `api / services / repository / models / schemas`.
Так модули переезжают в общую CRM целиком, а не разбираются по слоям.
